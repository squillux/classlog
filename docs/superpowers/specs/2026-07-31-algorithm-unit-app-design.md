# 중학교 정보 3단원 '알고리즘과 프로그래밍' 수업용 웹앱 — 설계

- 작성일: 2026-07-31
- 상태: 승인됨. 1단계 구현 대기
- 저장소: https://github.com/squillux/classlog

## Context

중학교 정보과목 3단원 수업에서 교과서 활동을 실습하려면 학생들이 매 차시마다
서로 다른 웹사이트에 접속해야 한다. 주소를 불러주고, 접속을 확인하고, 헤매는
학생을 챙기는 데 수업 시간이 새어 나간다. 결과물도 사이트마다 흩어져 있어
교사가 모아 볼 수 없다.

목표는 3단원 활동을 **하나의 주소 안에서** 끝내고, 학생 제출물이 **교사 화면
한 곳에** 모이게 하는 것이다. 현재 저장소에는 Vite + React + TS + Supabase
뼈대만 있고 화면은 제목 하나뿐이다. 여기서부터 쌓아 올린다.

## 확정된 요구사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 코드 실행 런타임 | **없음** | 블록코딩은 엔트리에서 별도 실습. Pyodide·Blockly 모두 불필요 |
| 활동 | 순서도/의사코드, 알고리즘 시각화, 퀴즈·빈칸, 미니게임 4종 | 교사가 선택 |
| 학생 인증 | 학급 코드 + 이름/번호. 계정·비밀번호 없음 | 개인정보 최소화, 수업 중 로그인 장애 회피 |
| 교사 기능 | 학급 개설 + 제출물 확인 | 문항 저작 화면은 만들지 않음 |
| 문항·과제 | 앱에 데이터 파일로 내장 | 저작 화면을 빼면 개발량이 크게 준다 |
| 기준 기기 | 학교 PC실 데스크톱 | 태블릿 대응은 이후 |
| 일정 | 기한 없음 | 단계별로 하나씩 완성해 나간다 |

## 범위 밖

블록 에디터, 코드 실행, 교사용 문항 저작 화면, 실시간 진도 현황, 성적 산출,
학부모 조회. 넣지 않는다.

## 아키텍처

기존 뼈대를 그대로 쓰고 라우팅과 상태만 얹는다.

```
src/
├─ main.tsx              라우터 마운트
├─ routes/
│  ├─ Home.tsx           학급 코드 입력
│  ├─ StudentShell.tsx   학생 레이아웃 (활동 목록 → 활동)
│  ├─ TeacherLogin.tsx
│  └─ TeacherDashboard.tsx
├─ activities/           활동 하나당 폴더 하나
│  ├─ quiz/
│  ├─ minigame/
│  ├─ visualizer/
│  └─ flowchart/
├─ content/              문항·과제 데이터 (TS 파일, 타입 있음)
├─ lib/
│  ├─ supabase.ts        (있음)
│  ├─ session.ts         학생 세션 (학급코드 + 익명 uid)
│  └─ submission.ts      제출물 저장/조회 단일 창구
└─ components/           공용 UI
```

**활동 인터페이스**가 이 설계의 핵심이다. 활동 4종은 서로 아무것도 공유하지
않고, 오직 아래 계약만 지킨다.

```ts
type Activity = {
  id: string
  title: string
  Component: React.FC<{ onSubmit: (answer: unknown) => void }>
}
```

활동은 자기가 뭘 하는지만 알고, 저장·인증·라우팅은 모른다. 덕분에 활동 하나를
추가하거나 갈아엎어도 나머지가 흔들리지 않고, 활동별로 따로 테스트할 수 있다.

**의존 추가**: `react-router`, `@xyflow/react`(순서도 에디터, 4단계에서),
`vitest` + `@testing-library/react`(테스트).

## 데이터 모델 (Supabase)

```sql
classes      id, code(unique), name, teacher_id, created_at
students     id, class_id, display_name, number, anon_uid
submissions  id, student_id, activity_id, payload(jsonb), created_at
```

- **교사**: Supabase Auth 이메일/비밀번호 로그인. 교사 계정은 Supabase 대시보드
  에서 직접 만든다. 회원가입 화면은 만들지 않는다 — 쓸 사람이 한 명이다.
- **학생**: `signInAnonymously()` 로 익명 uid를 받아 `students.anon_uid` 에 묶는다.
  비밀번호 없이도 RLS를 걸 수 있는 유일한 방법이다.
- **RLS**: 학생은 자기 `student_id` 의 제출물만 읽고 쓴다. 교사는 자기가 만든
  학급의 제출물만 읽는다. 학급 코드를 안다고 남의 답이 보이면 안 된다.

**학생 재입장 문제.** 익명 uid는 브라우저 저장소에 묶여 있어 다음 시간에 다른
자리에 앉거나 저장소가 지워지면 사라진다. 그대로 두면 같은 학생이 매번 새 학생
으로 잡혀 제출물이 흩어진다. 그래서 학생 식별은 `(class_id, number)` 조합을
기준으로 하고, `anon_uid` 는 입장할 때마다 그 행에 덮어쓴다. 즉 번호가 곧 신원
이고 익명 uid는 이번 접속의 열쇠일 뿐이다.

이 방식은 학생이 남의 번호를 입력하면 그 사람 행세를 할 수 있다는 뜻이기도 하다.
수업용 도구로는 감수할 만한 위험이라고 보고 넘어간다. 성적에 반영할 자료를
모으게 되면 그때 다시 봐야 한다.

`payload` 를 jsonb 로 둔 이유는 활동마다 답의 모양이 전혀 다르기 때문이다.
퀴즈는 선택지 번호, 순서도는 노드·엣지 그래프다. 활동별 테이블을 나누면
활동을 추가할 때마다 스키마 변경이 따라온다.

## 활동 설계

### 1. 퀴즈·빈칸 채우기

객관식과 빈칸 채우기. 즉시 정오 표시, 제출물 저장. 가장 단순해서 **전체
파이프라인(학급 입장 → 활동 → 저장 → 교사 확인)을 처음 관통하는 데 쓴다.**

### 2. 미니게임 3종

교과서 활동을 컴퓨팅 사고 요소에 하나씩 대응시킨다.

| 게임 | 학습 요소 | 형태 |
|---|---|---|
| 햄버거 만들기 | 문제 분해 · 순차 구조 | 재료를 순서대로 쌓고 절차를 확정 |
| 강 건너기 | 핵심 요소 골라내기 | 제약 조건 아래 이동 절차 찾기, 규칙 위반 시 되돌리기 |
| 틱택토 | 반복되는 패턴 찾기 · 조건 판단 | 이기는 규칙을 학생이 말로 정리해 제출 |

게임은 승패가 아니라 **학생이 찾아낸 규칙·절차**를 제출물로 남기는 것이 목적이다.

### 3. 알고리즘 시각화

정렬(선택·버블)과 순차 탐색의 동작을 막대 그래프로 보여준다. 재생/일시정지/
한 단계씩/속도 조절. 학생은 관찰한 내용을 짧게 적어 제출한다. 애니메이션은
상태 배열의 스냅샷 목록을 미리 만들어 두고 인덱스만 움직이는 방식으로 만든다 —
되감기와 단계 이동이 공짜로 따라온다.

### 4. 순서도/의사코드 작성

`@xyflow/react` 로 시작/처리/판단/종료 도형을 끌어다 놓고 선으로 잇는다.
저장 시 노드·엣지를 그대로 jsonb 에 넣는다. **네 활동 중 가장 크다.** 그래서
마지막에 만든다.

## 구현 순서

각 단계는 그 자체로 수업에 쓸 수 있는 상태로 끝난다.

1. **기반 + 퀴즈** — 라우팅, 학급 코드 입장, 익명 세션, Supabase 스키마와 RLS,
   제출물 저장, 최소 교사 대시보드, 퀴즈 활동. 여기서 파이프라인 전체를 검증한다.
2. **미니게임 3종** — 활동 인터페이스가 실제로 버티는지 확인하는 단계이기도 하다.
3. **알고리즘 시각화**
4. **순서도 에디터**
5. **다듬기** — 태블릿 레이아웃, 교사 대시보드 보강

## 검증

- **단위 테스트**: Vitest + Testing Library. 활동 컴포넌트는 각각 독립적으로
  테스트한다. 게임 규칙(강 건너기 유효 이동, 틱택토 승리 판정)과 정렬 스냅샷
  생성은 순수 함수로 분리해 테스트한다.
- **RLS 검증**: 다른 학급 코드로 들어간 세션에서 남의 제출물이 조회되지 않는지
  실제 쿼리로 확인한다. 이건 반드시 눈으로 봐야 한다.
- **실제 실행**: 각 단계마다 `npm run build` 통과 후 헤드리스 Chrome 으로
  학생 흐름(코드 입력 → 활동 → 제출)과 교사 흐름(로그인 → 제출물 확인)을
  끝까지 밟고 스크린샷으로 확인한다.
- **수업 전 리허설**: 1단계 완료 시점에 PC실에서 실제 기기로 한 반 분량을
  돌려본다. 기기 사양이 아직 확인되지 않았으므로 이때 함께 확인한다.

## 열린 항목

- 학교 PC실 기기·브라우저 버전 미확인. 1단계 리허설 때 확인하고 필요하면
  빌드 타깃을 낮춘다.
- 퀴즈 문항과 순서도 과제의 실제 내용은 교과서를 보고 채워야 한다. 1단계에서는
  샘플 3문항으로 파이프라인만 검증한다.
