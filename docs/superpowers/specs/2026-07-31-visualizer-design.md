# 3단계: 알고리즘 시각화 — 설계

- 작성일: 2026-07-31
- 상태: 승인됨. 구현 계획 대기
- 선행: [1단계 설계](2026-07-31-algorithm-unit-app-design.md), [2단계 설계](2026-07-31-minigames-design.md) — 모두 구현 완료

## Context

지금 활동은 퀴즈·강 건너기·틱택토 셋이다. 셋 다 학생이 규칙을 찾아내는
활동이고, **알고리즘이 실제로 어떻게 도는지 보는 활동은 없다.**

3단계는 정렬과 탐색이 한 단계씩 진행되는 모습을 막대 그래프로 보여준다.
목표는 "정렬을 할 줄 아는 것"이 아니라 **두 방법이 어떻게 다른지 눈으로 보고
말로 설명하는 것**이다.

4단계(순서도/의사코드 작성)는 별도 설계·계획으로 진행한다. `@xyflow/react`
라는 새 라이브러리를 들여와야 하고 공유하는 코드가 없다.

## 확정된 요구사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 화면 구성 | 한 화면에서 알고리즘을 골라 본다 | 오가며 비교해야 차이가 보인다 |
| 데이터 | 반 전체가 같은 값으로 고정 | 칠판에 같이 그리며 설명할 수 있다 |
| 제출물 | 객관식 2 + 서술형 1 | 비교를 강제한다. 일부는 자동 채점 |
| 문항 열림 조건 | 세 알고리즘을 모두 끝까지 본 뒤 | 안 보고 찍는 것을 막는다 |
| 애니메이션 | 스냅샷을 미리 만들고 인덱스만 움직인다 | 되감기·단계 이동이 공짜로 따라온다 |

## 범위 밖

정렬 알고리즘 추가(삽입·병합·퀵), 학생이 데이터를 직접 입력, 두 알고리즘
나란히 놓고 동시 재생, 실행 시간 측정. 넣지 않는다.

## 데이터

```ts
export const BARS = [5, 2, 8, 1, 9, 3, 7, 4]
export const SEARCH_TARGET = 7   // 인덱스 6. 뒤쪽에 있어 비교 과정이 보인다.
```

이 값으로 세 알고리즘을 돌리면 이렇게 된다. **구현 후 테스트가 이 숫자를
그대로 확인한다.**

| 알고리즘 | 비교 | 교환 | 결과 |
|---|---|---|---|
| 선택정렬 | 28 | 5 | 1,2,3,4,5,7,8,9 |
| 버블정렬 (조기 종료) | 25 | 13 | 1,2,3,4,5,7,8,9 |
| 순차 탐색 (7 찾기) | 7 | — | 인덱스 6에서 찾음 |

**이 숫자가 이 활동의 핵심이다.** 선택정렬은 비교를 더 많이 하는데 교환은
훨씬 적다. "어느 쪽이 더 빠른가"에 간단한 답이 없다는 것을 학생이 숫자로
마주하게 된다.

## 스냅샷

```ts
export type Step = {
  array: number[]
  comparing: number[]    // 지금 보고 있는 자리
  settled: number[]      // 이미 자리 잡은 구간
  found: number | null   // 탐색에서 찾은 자리
  comparisons: number
  swaps: number
  caption: string        // "5와 2를 비교합니다"
}

selectionSortSteps(input: number[]): Step[]
bubbleSortSteps(input: number[]): Step[]
linearSearchSteps(input: number[], target: number): Step[]
```

세 함수는 화면을 모르는 순수 함수다. 재생은 `steps[i]` 를 그리고 `i` 를 올릴
뿐이라, 되감기·한 단계씩·처음으로가 따로 만들 것 없이 따라온다.

**자막(`caption`)을 반드시 채운다.** 무엇을 보고 있는지 모르면 막대가 그냥
움직이는 그림일 뿐이다. 버블정렬이 한 바퀴 동안 한 번도 바꾸지 않아 멈출
때는 "한 번도 바꾸지 않았으므로 정렬이 끝났습니다"라고 알린다.

## 화면

- **위**: 알고리즘 세 개를 고르는 버튼. 끝까지 본 것에는 표시가 붙는다.
- **가운데**: 막대 그래프. 상태를 색으로 구분한다. 색은 장식용
  팔레트(`--accent-*`)에서 가져온다 — 파랑(`--primary`)은 동작 버튼에만 쓰는
  규칙을 지킨다.

  | 상태 | 색 |
  |---|---|
  | 그냥 있는 막대 | `--ink-faint` |
  | 지금 비교 중 | `--accent-orange` |
  | 자리 잡음 | `--accent-green` |
  | 탐색에서 찾음 | `--accent-pink` |
- **아래**: 자막 한 줄, 비교·교환 횟수, 재생 조작.

조작은 재생/일시정지 · 한 단계 뒤로 · 한 단계 앞으로 · 처음으로 · 속도
3단계(느리게 900ms / 보통 500ms / 빠르게 200ms)다.

알고리즘을 바꾸면 인덱스가 0으로 돌아가고 재생이 멈춘다. 보던 것을 잃지 않게
"끝까지 봤는지"는 알고리즘별로 따로 기억한다.

## 제출물

세 알고리즘을 모두 끝까지 본 뒤에 문항이 열린다. 그 전에는
"3개 중 2개 관찰함"으로 남은 것을 알린다.

1. 선택정렬과 버블정렬 중 **교환을 더 많이 한** 것은? (객관식 → 버블정렬)
2. 순차 탐색이 7을 찾기까지 **몇 번 비교**했나요? (객관식 → 7번)
3. 두 정렬 방법의 차이를 설명해 보세요. (서술형)

```ts
result: {
  watched: string[]                     // 끝까지 본 알고리즘 id
  replays: number                       // 처음부터 끝까지 돌려본 총 횟수
  quiz: { answers, score, total }
}
solved: true                            // 여기까지 왔다는 것은 다 봤다는 뜻
attempts: replays                       // 몇 번 돌려봤는지
note: 서술형 답 — 교사 화면에서 바로 읽힌다
```

`attempts` 를 "끝까지 본 알고리즘 수"로 두려다 바꿨다. 문항이 세 개를 다 본
뒤에만 열리므로 그 값은 언제나 3이어서 아무것도 알려주지 않는다. 대신 **총
재생 횟수**를 담는다. 여덟 번 돌려본 학생과 세 번 만에 넘어간 학생을 선생님이
구분할 수 있다.

**"끝까지 봤다"의 뜻**: 그 알고리즘의 마지막 스냅샷에 도달한 것. 재생으로
갔든 한 단계씩 눌러 갔든 똑같이 친다.

## 코드 구조

```
src/activities/
├─ shared/
│  ├─ payload.ts            (있음)
│  ├─ ReflectionForm.tsx    (있음)
│  ├─ questions.ts          ← river/grading.ts 에서 옮김
│  └─ QuestionSet.tsx       ← river/FinalQuiz.tsx 에서 옮김
├─ river/
│  └─ grading.ts            빈칸 로직만 남는다
└─ visualizer/
   ├─ data.ts               BARS, SEARCH_TARGET
   ├─ steps.ts              세 알고리즘의 스냅샷 생성 (순수 함수)
   ├─ content.ts            마무리 문항
   ├─ Bars.tsx              막대 그래프
   ├─ Player.tsx            재생 조작
   └─ VisualizerActivity.tsx
```

**공유 코드 정리를 함께 한다.** 마무리 문항 화면(`FinalQuiz`)과 채점
함수(`gradeFinal`)가 지금 `river/` 안에 있는데 시각화도 똑같은 것이 필요하다.
복사하면 두 벌이 따로 굳는다. `shared/` 로 옮겨 둘이 함께 쓴다. 강 건너기의
빈칸 로직(`checkBlank`, `allBlanksCorrect`, `splitSentence`)은 그 활동만의
것이라 `river/` 에 남긴다.

`Bars` 와 `Player` 를 따로 둔 이유는 둘의 관심사가 다르기 때문이다. `Bars` 는
`Step` 하나를 받아 그리기만 하고, `Player` 는 인덱스와 재생 상태만 다룬다.
어느 쪽도 알고리즘을 모른다.

## 검증

- **스냅샷 함수**: 마지막 단계의 배열이 정렬되어 있는지, 위 표의 비교·교환
  횟수와 정확히 같은지, 선택정렬이 버블정렬보다 교환이 적은지, 탐색이 찾은
  자리에서 멈추는지. 모든 단계에서 배열 길이와 원소 구성이 변하지 않는지.
- **화면**: Testing Library 로. 알고리즘을 바꾸면 처음으로 돌아가는지, 세 개를
  다 보기 전에는 문항이 잠겨 있는지 포함.
- **실제 실행**: Chrome 을 몰아 세 알고리즘을 끝까지 재생하고 제출까지 밟는다.
  2단계에서 쓴 CDP 스크립트 방식을 그대로 쓴다.

## 열린 항목

- 고정 데이터 `[5, 2, 8, 1, 9, 3, 7, 4]` 와 목표값 7은 교과서와 다를 수 있다.
  `src/activities/visualizer/data.ts` 한 곳만 고치면 되고, 테스트의 기대
  횟수도 함께 고쳐야 한다.
- 속도 3단계(900/500/200ms)는 근거 있는 값이 아니다. 수업에서 보고 조절한다.
