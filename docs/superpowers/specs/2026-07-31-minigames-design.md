# 2단계: 미니게임 3종 — 설계

- 작성일: 2026-07-31
- 상태: 승인됨. 구현 계획 대기
- 선행: [1단계 설계](2026-07-31-algorithm-unit-app-design.md) — 기반과 퀴즈는 구현 완료

## Context

1단계로 학급 입장·퀴즈·제출물 수집·교사 확인이 동작한다. 활동은 퀴즈 하나뿐이라
아직 "알고리즘과 프로그래밍" 수업의 알맹이가 없다.

2단계는 교과서 활동 셋을 넣어 학생이 **규칙과 절차를 스스로 찾아내는** 경험을
하게 한다. 세 게임은 각각 다른 컴퓨팅 사고 요소를 맡는다. 승패가 목적이 아니라,
학생이 찾아낸 규칙을 말로 정리해 남기는 것이 목적이다.

## 확정된 요구사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 제출물 구성 | 학생이 쓴 설명 + 최종 답 + 플레이 기록, 셋 다 | 설명이 핵심이고 나머지는 맥락을 준다 |
| 틱택토 상대 | 컴퓨터 | 혼자 앉은 PC에서 반복해야 패턴이 보인다 |
| 컴퓨터 실력 | 일부러 빈틈 있게 | 완벽한 틱택토는 절대 지지 않아 학생이 이길 기회가 없다 |
| 판 수 | 게임당 문제 하나 | 빨리 끝내고 설명 쓰는 데 시간을 쓴다 |
| 틱택토만 예외 | 다시 하기 허용, 제출은 한 번 | 한 판이 1분도 안 걸려 한 번으로는 규칙을 못 찾는다 |
| 조작 방식 | 클릭. 드래그 안 씀 | 학교 PC 마우스와 태블릿 양쪽에서 드래그는 실패율이 높다 |

## 범위 밖

교사용 문항 저작, 활동 배정(어떤 활동을 열어둘지 고르기), 난이도 단계, 순위표,
저장 후 이어하기. 넣지 않는다.

활동 배정은 2단계가 끝나 활동이 넷이 된 뒤에 별도로 설계한다.

## 게임 1 — 햄버거 만들기

**학습 요소**: 문제 분해 · 순차 구조

**규칙.** 재료 7개가 섞인 채로 놓여 있다. 클릭하면 아래부터 차곡차곡 쌓인다.
맨 위 재료를 다시 클릭하면 빠진다. 정답 순서와 정확히 일치해야 통과한다.

정답 순서(아래 → 위): `아래빵 · 소스 · 양상추 · 토마토 · 패티 · 치즈 · 위빵`

**판정**: 7개를 다 쌓으면 자동으로 맞는지 알린다. 틀리면 시도 횟수가 하나 늘고
다시 쌓을 수 있다.

**설명 질문**: "왜 이 순서여야 할까요? 순서를 바꾸면 어떤 일이 생기나요?"

## 게임 2 — 강 건너기

**학습 요소**: 핵심 요소 골라내기

**규칙.** 농부가 늑대·양·양배추를 강 건너로 옮긴다. 배에는 농부와 물건 하나만
탄다. 농부가 없는 쪽에서는

- 늑대와 양이 같이 있으면 → 양이 잡아먹힌다
- 양과 양배추가 같이 있으면 → 양배추가 먹힌다
- 늑대와 양배추는 같이 둬도 괜찮다

**조작**: 이쪽 편의 물건을 클릭해 배에 태우고 "건너가기"를 누른다. 아무것도 안
태우고 혼자 건널 수도 있다.

**규칙을 어겼을 때**: 벌점을 주지 않는다. 수를 되돌리고 왜 안 되는지 알린다
("농부가 없으면 늑대가 양을 잡아먹습니다"). 실패가 곧 학습인 활동이다. 어긴
횟수는 기록에 남는다.

**최소 해**: 7수

```
양 건너감 → 농부 혼자 돌아옴 → 늑대 건너감 → 양 데리고 돌아옴
→ 양배추 건너감 → 농부 혼자 돌아옴 → 양 건너감
```

**설명 질문**: "이 문제를 풀 때 꼭 기억해야 하는 규칙은 무엇이었나요?"

## 게임 3 — 틱택토

**학습 요소**: 반복되는 패턴 찾기 · 조건 판단

**규칙.** 3×3. 학생이 O로 먼저 두고 컴퓨터가 X로 둔다. 가로·세로·대각선으로
세 개를 잇거나 아홉 칸이 다 차면 끝난다. "다시 하기"로 몇 판이든 둘 수 있고,
전적(승·무·패)이 화면에 쌓인다. 제출은 한 번이다.

**컴퓨터가 수를 고르는 순서**

1. 한 수로 이길 수 있으면 그 자리에 둔다
2. 학생이 다음 수로 이기면 그 자리를 막는다
3. 아니면 빈 칸 중 아무 데나 둔다

다만 매 수마다 정해진 확률(35%)로 1·2단계를 건너뛰고 아무 데나 둔다. 이것이
학생이 이길 수 있는 빈틈이다. 확률은 상수 하나로 두어 수업 반응을 보고
조절할 수 있게 한다.

**설명 질문**: "이기는 방법을 찾았나요? 규칙으로 말해 보세요."

## 제출물

세 게임이 같은 모양으로 낸다.

```ts
type MinigamePayload = {
  solved: boolean     // 해냈는가 (틱택토는 한 번이라도 이겼는가)
  attempts: number    // 시도 횟수 (틱택토는 둔 판 수)
  elapsedMs: number   // 활동을 연 뒤 제출까지 걸린 시간
  result: unknown     // 게임별 기록
  note: string        // 학생이 쓴 설명
}
```

`result` 의 게임별 모양:

| 게임 | result |
|---|---|
| 햄버거 | `{ order: string[] }` — 마지막으로 쌓은 재료 id 를 아래부터 나열 |
| 강 건너기 | `{ moves: string[]; violations: number }` |
| 틱택토 | `{ wins: number; draws: number; losses: number; lastBoard: (\|'O'\|'X'\|null)[] }` |

강 건너기의 `moves` 는 한 수를 한 문자열로 적는다. 형식은 `<태운 것>:<방향>`
이고 방향은 `건너감` 또는 `돌아옴`, 아무것도 안 태웠으면 `혼자` 로 적는다.
7수 정답은 이렇게 남는다.

```
["양:건너감", "혼자:돌아옴", "늑대:건너감", "양:돌아옴",
 "양배추:건너감", "혼자:돌아옴", "양:건너감"]
```

`violations` 는 규칙을 어겨 되돌린 횟수다. 되돌린 수는 `moves` 에 남기지 않는다.

설명 입력은 **공통 컴포넌트 하나**(`ReflectionForm`)로 만들어 셋이 같이 쓴다.
게임마다 묻는 문장만 다르게 넘긴다. 설명이 비어 있으면 제출할 수 없다 —
이 활동의 목적이 설명이기 때문이다.

**재제출은 막지 않는다.** 활동을 다시 열어 또 낼 수 있고, 그때마다 제출물이
한 줄씩 쌓인다. 1단계 동작 그대로다. "제출은 한 번"은 학생에게 권하는 흐름이지
앱이 강제하는 규칙이 아니다. 잘못 낸 학생이 다시 낼 길을 막지 않기 위해서다.

## 코드 구조

```
src/activities/
├─ types.ts                      (있음) Activity 인터페이스
├─ index.ts                      (있음) 레지스트리 — 활동 3개 추가
├─ shared/
│  ├─ ReflectionForm.tsx         설명 입력 + 제출 버튼
│  └─ payload.ts                 MinigamePayload 타입과 조립 함수
├─ burger/
│  ├─ rules.ts                   정답 순서, 순서 검사
│  └─ BurgerActivity.tsx
├─ river/
│  ├─ rules.ts                   상태·이동·위반 판정
│  └─ RiverActivity.tsx
└─ tictactoe/
   ├─ rules.ts                   승패 판정, 컴퓨터 수 고르기
   └─ TicTacToeActivity.tsx
```

**규칙은 전부 `rules.ts` 에 순수 함수로 둔다.** 화면 없이 테스트할 수 있어야
한다. 1단계에서 `gradeQuiz` 를 컴포넌트에서 떼어낸 것과 같은 이유다.

컴퓨터 수 고르기는 난수를 쓰므로 `chooseComputerMove(board, rng)` 처럼 난수원을
인자로 받는다. 테스트에서 정해진 값을 주면 결과가 결정적이 된다.

각 활동은 기존 `Activity` 인터페이스만 지킨다. 레지스트리에 한 줄씩 더하는 것
외에 1단계 코드는 건드리지 않는다. 이 인터페이스가 실제로 버티는지 확인하는
단계이기도 하다.

## 교사 화면 보완

**이번 단계에 함께 넣는다.** 미루면 학생이 쓴 설명을 아무도 읽을 수 없다.

지금 교사 화면은 제출물을 표로만 보여주고 속을 못 본다. 퀴즈는 점수만 봐도
되지만 미니게임의 알맹이는 학생이 쓴 글이다.

- 표의 한 줄을 누르면 아래로 펼쳐져 **학생이 쓴 설명**과 기록(성공 여부, 시도
  횟수, 걸린 시간)을 보여준다
- 점수 칸은 퀴즈면 `2 / 3`, 미니게임이면 `성공` 또는 `미완`으로 표시한다.
  `payload` 에 `score` 가 있으면 점수로, `solved` 가 있으면 성공 여부로 읽는다
- 활동 칸에 `quiz` 같은 id 대신 활동 이름을 보여준다. 레지스트리에서 찾는다

## 구현 순서

각 단계 끝에서 테스트가 통과하고 앱이 돈다.

1. **공통 뼈대** — `MinigamePayload`, `ReflectionForm`
2. **햄버거 만들기** — 가장 단순해서 공통 뼈대가 맞는지 먼저 확인한다
3. **강 건너기**
4. **틱택토**
5. **교사 화면 보완** — 제출물 자세히 보기, 점수 칸, 활동 이름

## 검증

- **규칙 순수 함수**: 강 건너기의 위반 조합 전부와 7수 정답 경로, 틱택토의
  승리 8줄과 "이길 수를 실제로 고르는가 / 막을 수를 실제로 막는가", 햄버거
  순서 판정. 난수는 고정한 rng 를 주입해 결정적으로 검사한다.
- **화면**: Testing Library 로 각 활동을 독립적으로. 설명이 비면 제출이
  막히는지 포함.
- **실제 실행**: Chrome 을 몰아 세 게임을 실제로 풀고 제출까지 밟는다.
  1단계에서 쓴 방식(폼을 실제로 채워 넣는 CDP 스크립트)을 그대로 쓴다.
- **교사 화면**: 미니게임 제출물이 실제로 펼쳐져 학생 설명이 보이는지 눈으로
  확인한다.

## 열린 항목

- 틱택토 컴퓨터의 실수 확률 35%는 근거 있는 값이 아니다. 수업에서 써 보고
  학생이 너무 쉽게 이기거나 한 번도 못 이기면 상수를 조절한다.
- 햄버거 정답 순서는 하나로 고정한다. 실제로는 다른 순서도 말이 되지만,
  순차 구조를 가르치는 활동이라 명확한 정답이 낫다. 설명 질문에서 "순서를
  바꾸면 어떻게 되는지" 묻는 것으로 이 여지를 다룬다.
